# PPT 解析（切图 + 单页总结 + 项目画像）需求分析分档

> 输入样例：`docs/ChatBI产品介绍_2025.pptx`  
> 目标：对项目类 PPT 做“逐页可追溯”的结构化理解与总结输出，沉淀可复用的项目画像。

## 1. 背景与目标

给定一个项目介绍类 PPTX，需要实现一条自动化流水线：

1) 把每一页 slide 切图（用于视觉信息保真）  
2) 基于每张图生成该页的语言描述总结（可读、可检索、可追溯）  
3) 再根据全量内容整理输出“项目画像”（结构化要点 + 证据页码）

核心目标：

- **可追溯**：任何结论都能回到具体 slide（页码/图片/可选的文本抽取）  
- **可批处理**：支持对单个或多个 PPT 批量跑通，产物可复用  
- **可运营**：支持增量更新（同一 PPT 变更后只重算受影响页）和质量评估

## 2. 范围与非目标

### 2.1 范围（本需求覆盖）

- PPTX → 逐页导出图片（PNG/JPG）
- 单页“描述总结”生成（面向人读/面向检索的两种形式）
- 文档级“项目画像”生成（结构化字段 + 引用证据）
- 产物落盘（文件 + JSON/Markdown），并能复跑、可幂等

### 2.2 非目标（本期不强制）

- 做成完整知识库/RAG 检索系统（可作为后续对接方向）
- 自动生成高保真矢量重排版/可编辑的 PPT（不做）
- 复杂的版式/图表数据结构化还原（仅做“解释性摘要”，V2 再增强）

## 3. 使用者与典型场景

- 售前/产品：快速理解项目 PPT，生成对外口径要点
- 交付/支持：提炼部署架构、依赖、约束、边界条件
- 管理/投标：抽取项目定位、差异化、价值、案例证据

## 4. 输入、输出与目录约定

### 4.1 输入

- `*.pptx`（建议同时包含“备注/讲稿”，可显著提升总结质量）

### 4.2 输出（建议目录结构）

以输入文件基名 `ChatBI产品介绍_2025` 为例：

- `ppt_outputs/ChatBI产品介绍_2025/`
  - `slides/`
    - `001.png` … `NNN.png`
  - `page_summaries/`
    - `001.json`（结构化单页总结，含证据与置信度）
    - `001.md`（单页可读版）
  - `doc_summary/`
    - `project_profile.json`（项目画像：结构化）
    - `project_profile.md`（项目画像：可读版）
  - `manifest.json`（运行元数据：hash、版本、耗时、错误页等）

> 说明：如果仓库已有其它产物目录，可在实现时再对齐；此处是建议的可维护结构。

## 5. 总体流程（逻辑）

```text
PPTX
  │
  ├─(A) Slide 渲染：PPTX → 每页图片（带页码映射）
  │        │
  │        └─ 质量检测：空白/异常页、分辨率、尺寸一致性
  │
  ├─(B) 单页总结：图片(+可选页标题/讲稿/文本框) → page_summary
  │        │
  │        └─ 输出：结构化 JSON + 可读 Markdown（含引用 slide_no）
  │
  └─(C) 项目画像：全量 page_summary → project_profile
           └─ 输出：结构化 JSON + 可读 Markdown（含证据 slide_no 列表）
```

## 6. 功能需求（按模块）

### 6.1 Slide 切图（渲染）

**FR-IMG-01**：支持读取 `*.pptx`，按 slide 顺序导出图片（默认 PNG）。  
**FR-IMG-02**：图片命名包含 slide 序号（从 1 开始，固定宽度补零）。  
**FR-IMG-03**：支持配置渲染分辨率/缩放（如 1x/2x），保证文本可读。  
**FR-IMG-04**：输出 `manifest.json`，至少记录：

- 输入文件路径、文件 hash、导出时间、页数
- 每页图片路径、像素尺寸、导出是否成功、错误信息（如有）

**实现注意（需求层面约束）**

- 纯 Python 的 `python-pptx` 只能读结构，**无法高保真渲染**；通常需要：
  - LibreOffice/PowerPoint（headless）导出图片，或
  - 先转 PDF 再逐页转图片（同样依赖转换器）
- 渲染链路应可插拔（不同环境使用不同 renderer），对上层总结模块透明。

### 6.2 单页“语言描述总结”

**FR-SUM-01**：对每张 slide 图片生成“单页总结”，至少包含：

- `slide_no`：页码
- `title`：该页标题（可从 PPT 文本抽取或模型生成）
- `one_liner`：一句话总结（≤ 30 字，便于目录/检索）
- `bullets`：要点列表（建议 3–7 条）
- `details`：补充说明（可选，1–2 段）
- `entities`：关键实体（产品名/模块/客户/指标/技术名词等，允许为空）
- `signals`：该页类型/意图标签（如：定位、架构、功能、案例、竞品、报价、路线图等）
- `evidence`：证据（至少包含 `slide_no`；可扩展为 bbox/OCR 片段）
- `confidence`：0–1（低置信度页可标记需人工复核）

**FR-SUM-02**：支持“文本增强输入”（可选项，但建议纳入 V1）：

- PPT 页标题、文本框内容、备注/讲稿（speaker notes）
- 这些文本与图片共同作为模型输入，提高准确性并降低幻觉风险

**FR-SUM-03**：失败降级与重试：

- 单页失败不影响全局任务；错误页在 `manifest.json` 与汇总报告中可见
- 支持对失败页重跑（按页码）

### 6.3 文档级“项目画像”

项目画像是从全量单页总结中抽象出来的结构化描述，强调“可对外口径/可内部理解”的统一视图。

**FR-PRO-01**：输出 `project_profile.json`，建议字段：

- `project_name`（若 PPT 未明确，允许模型给出候选并标注不确定）
- `positioning`：产品/项目定位（一段话）
- `target_users`：目标用户/客户画像
- `core_value`：核心价值与收益（可量化指标优先）
- `core_capabilities`：核心能力清单（分组）
- `architecture`：架构/模块划分（解释性描述；V2 再做结构化拓扑）
- `deployment`：部署形态/依赖/环境要求（如有）
- `integrations`：对接系统/接口（如有）
- `differentiators`：差异化与竞品对比要点（如有）
- `cases`：案例/落地证据（客户、场景、效果）
- `risks_and_limits`：边界、风险、前置条件
- `open_questions`：PPT 未覆盖但画像需要的关键问题清单
- `evidence_map`：每个字段对应的证据 slide_no 列表

**FR-PRO-02**：输出 `project_profile.md`（可读版），包含：

- “结论摘要” + “证据索引（按字段列出页码）” + “待确认问题”

### 6.4 任务编排与运行方式

**FR-RUN-01**：提供最小可用运行入口（二选一即可）：

- CLI：如 `python -m ... --input docs/ChatBI产品介绍_2025.pptx --out ppt_outputs/...`
- 或 API：HTTP/函数调用方式（入参路径/出参目录）

**FR-RUN-02**：幂等与增量：

- 输入文件 hash 不变则跳过已成功的切图/总结步骤（可配置强制重跑）
- 允许只重算某几页（如 `--slides 3,7-9`）

## 7. 非功能需求

### 7.1 质量与一致性

- 结论必须可追溯到 slide_no；不确定内容要显式标注（如 `confidence < 0.5`）
- 输出语言风格统一（可通过模板/提示词约束）
- 关键术语一致（同一实体不要多种叫法；可通过术语表/后处理统一）

### 7.2 性能与资源

- 支持至少 1 个 PPT（~50 页）在可接受时间内完成（具体阈值由部署环境确定）
- 切图与单页总结支持并行（按页并发，受限于 CPU/GPU/模型 QPS）

### 7.3 可观测与可维护

- 每次任务产出 `manifest.json` 与简要统计（总页数、成功/失败、耗时）
- 日志至少包含：输入、输出目录、失败页码与异常栈（便于排障）

### 7.4 安全与合规（如果 PPT 含敏感信息）

- 支持对输出做脱敏/红线检测（例如客户名、金额、内网地址），命中则标记需人工确认
- 支持本地/内网模型调用（避免把敏感 PPT 发到公网）

## 8. 分档（MVP / V1 / V2）与交付物

### 8.1 MVP（跑通最短闭环）

目标：对单个 PPT 跑通“切图 → 单页总结 → 项目画像”，产物可落盘可复跑。

- 切图：PPTX 全量导出 `slides/*.png` + `manifest.json`
- 单页总结：每页生成 `page_summaries/{slide_no}.json`
- 项目画像：生成 `doc_summary/project_profile.json`
- 验收标准：
  - 页数一致（输入 slide 数 = 输出图片数）
  - 任意输出字段可定位到 `slide_no`
  - 存在失败页时，任务仍完成并给出失败清单

### 8.2 V1（可用性与可控性）

目标：提升总结准确性、可用性与可运营能力。

- 文本增强：抽取页标题/文本框/备注并参与单页总结（降低纯视觉误读）
- 输出双格式：每页 `json + md`；画像 `json + md`
- 增量能力：按文件 hash/页码跳过已完成步骤；支持指定页重跑
- 质量机制：低置信度页标记 + 汇总“需人工复核列表”
- 验收标准：
  - 同一 PPT 二次运行不重复计算（除非强制重跑）
  - 画像包含 `open_questions`，能指导补齐信息

### 8.3 V2（结构化理解与企业级能力）

目标：让“项目画像”更结构化、更可集成、更适合规模化运营。

- 图表/架构增强：对架构图、流程图、表格做更细结构化（节点/关系/表格字段）
- 术语与实体库：跨页实体归一、词表维护、同义词合并
- 输出可集成：对接知识库/RAG（向量化索引）、对接工单/审批流
- 合规增强：敏感项识别与脱敏策略、权限隔离与审计

## 9. 风险与对策（需求层）

- 渲染依赖风险：不同环境渲染效果差 → renderer 插拔 + 转 PDF 兜底
- 纯视觉总结幻觉：图表/小字易误读 → V1 引入“文本增强 + 低置信度提示”
- 成本与延迟：逐页调用多模态模型成本高 → 并发 + 缓存 + 只对关键页高精模式
- 敏感信息泄露：外部模型调用风险 → 支持本地/内网模型与脱敏检测

## 10. 需要确认的问题（建议在进入实现前澄清）

1) 输出语言：仅中文？是否需要中英双语？  
2) “项目画像”字段是否有固定模板/公司内部标准？  
3) 运行环境：是否允许安装 LibreOffice/PowerPoint（决定切图实现路径）？  
4) 模型调用：使用哪个多模态模型/接口？是否必须离线/内网？  
5) 对敏感信息的处理要求：是否需要自动脱敏/打码？
