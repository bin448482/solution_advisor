# Embedding系统测试方案

## 测试目标

验证M3E embedding + Chroma向量数据库的检索质量，确保RAG系统能够准确找到相关项目信息并支持语义查询。

## 测试环境

- **Embedding模型**: moka-ai/m3e-base (768维)
- **向量数据库**: Chroma
- **测试数据**: ppt_outputs目录下已处理的项目PPT
- **测试工具**: `python -m src.scripts.vectordb_cli query`

## 测试问题集

### 1. 直接事实查询（精确匹配）

**目的**: 测试系统能否找到明确提到的信息

| 问题 | 预期结果 | 评估标准 |
|------|---------|---------|
| ChatBI的核心功能是什么？ | 返回功能介绍相关的slide | top-1相似度>0.7 |
| ChatBI支持哪些数据源？ | 返回数据源/集成相关slide | 包含具体数据源列表 |
| ChatBI的目标用户是谁？ | 返回用户定位相关slide | 明确提到目标用户群体 |
| ChatBI的部署方式有哪些？ | 返回部署/架构相关slide | 列出部署选项 |

### 2. 概念性查询（语义理解）

**目的**: 测试系统对概念的语义理解能力

| 问题 | 预期结果 | 评估标准 |
|------|---------|---------|
| 哪个项目可以帮助企业做数据分析？ | 返回BI/分析类项目 | 语义匹配，非关键词匹配 |
| 有没有支持自然语言查询的产品？ | 返回NLP/对话相关功能 | 理解"自然语言"概念 |
| 哪些方案涉及到AI技术？ | 返回AI/ML相关项目 | 识别AI相关术语 |
| 什么产品适合非技术人员使用？ | 返回低代码/易用性相关 | 理解用户画像 |

### 3. 对比性查询（跨项目）

**目的**: 测试跨项目检索能力（如果有多个项目）

| 问题 | 预期结果 | 评估标准 |
|------|---------|---------|
| ChatBI和其他BI产品的区别是什么？ | 返回差异化/竞争力相关 | 包含differentiators信息 |
| 哪些项目提到了云原生架构？ | 返回多个项目的架构slide | 跨项目检索 |
| 不同项目的技术栈对比 | 返回技术架构相关slide | 覆盖多个项目 |

### 4. 细节查询（深度检索）

**目的**: 测试能否找到具体的技术细节

| 问题 | 预期结果 | 评估标准 |
|------|---------|---------|
| ChatBI使用了哪些AI模型？ | 返回技术细节slide | slide-level文档，高confidence |
| 系统的架构组件有哪些？ | 返回架构图/组件说明 | 包含具体组件列表 |
| 有哪些集成接口？ | 返回集成/API相关slide | 列出具体接口 |
| 性能指标是多少？ | 返回性能/指标相关slide | 包含具体数值 |

### 5. 边界情况（负面测试）

**目的**: 测试系统对不存在信息的处理

| 问题 | 预期结果 | 评估标准 |
|------|---------|---------|
| ChatBI的价格是多少？ | 低相似度或无结果 | 相似度<0.5或明确标识无信息 |
| ChatBI支持区块链吗？ | 低相似度或无结果 | 不返回不相关内容 |
| ChatBI的创始人是谁？ | 低相似度或无结果 | 避免幻觉回答 |

### 6. 模糊查询（同义词/近义词）

**目的**: 测试语义相似度能力

| 原文表述 | 查询表述 | 预期结果 |

| BI分析平台 | 数据可视化工具 | 能找到相关内容 |

| B2B产品 | 企业级应用 | 理解同义概念 |
| 低代码平台 | 无代码开发 | 识别相近概念 |

### 7. 多跳推理（间接信息）

**目的**: 测试需要综合多个信息点的查询

| 问题 | 需要综合的信息 | 评估标准 |

```python
import json

test_cases = [

        "passed": result[0]["score"] >= case["min_score"] if result else False
    })

# 输出测试报告
print(json.dumps(results, indent=2, ensure_ascii=False))
```

## 评估标准

### 定量指标

1. **相似度分数 (Similarity Score)**
   - 优秀: >0.8
   - 良好: 0.6-0.8
   - 可接受: 0.4-0.6
   - 差: <0.4

2. **Top-K准确率**
   - Top-1准确率: 最相关结果排在第1位的比例
   - Top-3准确率: 最相关结果排在前3位的比例
   - Top-5准确率: 最相关结果排在前5位的比例

3. **覆盖率**
   - Slide-level覆盖: 能找到具体slide的比例
   - Project-level覆盖: 能找到项目概述的比例

### 定性指标

1. **相关性 (Relevance)**
   - 返回的文档是否真正包含答案
   - 是否有无关文档混入

2. **排序质量 (Ranking Quality)**
   - 最相关的结果是否排在前面
   - 相似度分数是否合理反映相关性

3. **语义理解 (Semantic Understanding)**
   - 同义词查询是否有效
   - 概念性查询是否准确

4. **置信度一致性 (Confidence Consistency)**
   - 高confidence的文档是否排名更高
   - 低confidence的文档是否被适当降权

## 常见问题诊断

### 问题1: 相似度分数普遍偏低

**可能原因**:
- Embedding模型不适合当前领域
- 文档预处理质量差（噪声多、格式混乱）
- 查询表述与文档表述差异大

**解决方案**:
- 检查rag_documents.json中的text字段质量
- 考虑使用m3e-large模型
- 优化clean_summary_for_embedding逻辑

### 问题2: 返回结果不相关

**可能原因**:
- Metadata过滤不当
- 文档切分粒度不合理
- Embedding模型语义理解偏差

**解决方案**:
- 检查metadata字段是否正确
- 调整slide-level vs project-level的平衡
- 尝试不同的查询表述

### 问题3: 跨项目查询效果差

**可能原因**:
- 项目名称在文档中权重过高
- 缺少project-level概述文档
- Collection设计不支持跨项目检索

**解决方案**:
- 确保project-level文档已生成
- 调整文档text格式，降低项目名权重
- 考虑使用metadata过滤而非纯语义检索

## 优化建议

### 短期优化（无需改代码）

1. **调整查询表述**: 使用更接近文档的表述方式
2. **调整top-k值**: 增加返回结果数量以提高召回率
3. **使用metadata过滤**: 结合project_name、page_type等过滤

### 中期优化（需要调整配置）

1. **切换到m3e-large**: 更高维度，更好的语义理解
2. **调整batch_size**: 优化embedding生成速度
3. **启用GPU加速**: 使用cuda或mps设备

### 长期优化（需要改代码）

1. **改进文档预处理**: 优化clean_summary_for_embedding逻辑
2. **混合检索**: 结合全文检索和向量检索
3. **重排序模型**: 在向量检索后使用reranker
4. **查询扩展**: 自动生成同义查询
