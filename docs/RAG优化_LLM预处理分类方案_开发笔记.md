# RAG 优化：LLM 预处理分类方案

## 开发背景

**日期**：2026-01-02
**提出者**：用户需求
**当前问题**：M3E 向量模型在信息理解和专业知识方面存在缺陷

## 问题分析

### 当前 RAG 架构

```
PPT → 单页总结(PageSummary) → 按 slide 切分为 chunks → M3E 向量化 → ChromaDB
```

**现状**：
- 每个 slide 作为一个 chunk（粒度：slide-level）
- 使用 M3E（中文优化）生成 768 维向量
- 直接存储到 ChromaDB，依赖向量相似度检索

### 核心问题

1. **M3E 模型局限**：
   - 通用中文模型，未针对技术/商业领域微调
   - 对专业术语、行业知识理解不足
   - 语义相似度计算可能偏离业务相关性

2. **Chunk 无序性**：
   - Slide 按顺序存储，但向量空间中分布无序
   - 相关主题的 slides 可能在向量空间中距离较远
   - 检索时依赖纯向量相似度，缺乏结构化组织

3. **检索质量问题**：
   - 模糊查询可能召回不相关内容
   - 专业术语匹配不准确
   - 缺乏主题聚类和层次结构

## 提出方案

### 核心思路

**在向量化之前，使用 LLM 对 chunks 进行分类整理，使向量数据库中的数据呈现有序状态。**

### 方案设计

```
PPT → 单页总结 → LLM 分类整理 → 结构化 chunks → M3E 向量化 → ChromaDB（有序）
                    ↓
              按需求维度分类：
              - 功能模块
              - 技术架构
              - 部署运维
              - 案例场景
              - 产品定位
```

### 预期效果

1. **语义增强**：LLM 理解专业内容，生成更准确的分类标签
2. **结构化组织**：相同主题的 chunks 聚合在一起
3. **检索优化**：可以先按分类过滤，再进行向量检索
4. **降低对向量模型的依赖**：分类信息作为强信号，补充向量相似度

## 可行性评估

### ✅ 优势分析

#### 1. **LLM 理解能力强**
- GPT-4/Claude 等模型对技术文档理解准确
- 可以识别专业术语、技术栈、架构模式
- 能够理解上下文和隐含信息

#### 2. **分类维度灵活**
- 可以按多个维度同时分类（功能、技术、场景）
- 支持层次化分类（一级分类 → 二级分类）
- 可以根据业务需求动态调整分类体系

#### 3. **与现有架构兼容**
- 不改变 chunk 的基本结构
- 只是在 metadata 中增加分类信息
- 可以渐进式实施，不影响现有功能

#### 4. **检索性能提升**
- 分类过滤 + 向量检索 = 混合检索
- 减少向量检索的候选集，提高精度
- 支持"先粗筛后精排"的两阶段检索

### ⚠️ 挑战与风险

#### 1. **LLM 调用成本**
- **问题**：每个 chunk 都需要 LLM 分类，成本较高
- **影响**：
  - 单个项目 40 slides → 40 次 LLM 调用
  - 批量处理多个项目时成本显著
- **缓解方案**：
  - 批量分类（一次调用处理多个 slides）
  - 使用较小模型（如 GPT-4o-mini）
  - 缓存分类结果，避免重复调用

#### 2. **分类一致性**
- **问题**：LLM 输出可能不稳定，同一内容多次分类结果不同
- **影响**：
  - 分类标签不一致，影响检索
  - 难以维护统一的分类体系
- **缓解方案**：
  - 使用低 temperature（如 0.1）提高稳定性
  - 提供明确的分类标准和示例
  - 后处理归一化（映射到标准分类）

#### 3. **分类粒度选择**
- **问题**：分类过粗 → 区分度不够；分类过细 → 过拟合
- **影响**：
  - 粗分类：检索召回率高但精度低
  - 细分类：检索精度高但召回率低
- **缓解方案**：
  - 采用层次化分类（粗 → 细）
  - 支持多标签分类（一个 chunk 可属于多个类别）
  - 根据实际检索效果迭代调整

#### 4. **处理时间增加**
- **问题**：增加 LLM 分类步骤，pipeline 耗时增加
- **影响**：
  - 单个项目处理时间从 5 分钟 → 10 分钟
  - 批量处理时等待时间更长
- **缓解方案**：
  - 并行调用 LLM（多个 slides 同时分类）
  - 异步处理（先存储原始 chunks，后台分类）
  - 增量更新（只对新增/修改的 slides 重新分类）

#### 5. **分类错误处理**
- **问题**：LLM 可能误分类或无法分类某些内容
- **影响**：
  - 错误分类导致检索失败
  - 无法分类的 chunks 被遗漏
- **缓解方案**：
  - 设置"未分类"兜底类别
  - 记录分类置信度，低置信度人工审核
  - 支持手动修正分类

### 📊 技术可行性评分

| 维度 | 评分 | 说明 |
|------|------|------|
| **技术实现难度** | ⭐⭐⭐ (中等) | 需要设计分类体系、提示词工程、后处理逻辑 |
| **与现有架构兼容性** | ⭐⭐⭐⭐⭐ (优秀) | 只需在 RAG 准备阶段增加分类步骤 |
| **成本可控性** | ⭐⭐⭐ (中等) | LLM 调用成本需要优化，但可接受 |

**综合评分**：⭐⭐⭐⭐ (4/5) - **可行且推荐**

## 实施方案

### 阶段 1：最小可行方案（MVP）

**目标**：验证 LLM 分类的效果，不改变现有架构

**实施步骤**：
1. 在 `src/rag.py` 中增加 `classify_chunk_with_llm()` 函数
2. 定义基础分类体系（5-8 个一级分类）
3. 设计分类提示词（`src/prompts/chunk_classification_zh.txt`）
4. 在 `prepare_slide_embedding()` 中调用分类函数
5. 将分类结果存入 metadata 的 `llm_categories` 字段
6. 在 `ChromaStore.query_with_guardrails()` 中支持按分类过滤

**预期产出**：
- 新增字段：`metadata.llm_categories: List[str]`
- 检索支持：`query(..., where={"llm_categories": {"$contains": "architecture"}})`

**验证指标**：
- 分类准确率 > 85%（人工抽样验证）
- 检索精度提升 > 15%（对比实验）

### 阶段 2：优化与扩展

**优化方向**：
1. **批量分类**：一次 LLM 调用处理多个 slides
2. **层次化分类**：一级分类 → 二级分类
3. **多标签支持**：一个 chunk 可属于多个类别
4. **分类置信度**：记录 LLM 的分类置信度
5. **混合检索**：分类过滤 + 向量检索 + BM25 关键词

**扩展功能**：
1. **分类统计**：项目级别的分类分布可视化
2. **分类导航**：按分类浏览项目内容
3. **分类推荐**：根据用户查询推荐相关分类

### 阶段 3：高级特性

**探索方向**：
1. **知识图谱**：基于分类构建项目知识图谱
2. **关系抽取**：识别 chunks 之间的关系（依赖、引用、对比）
3. **主题聚类**：自动发现隐含主题，无需预定义分类
4. **个性化分类**：根据用户角色（开发/运维/销售）动态调整分类

  - id: positioning
    name: 产品定位

    name: 技术架构

  - id: deployment
    name: 部署运维
    description: 部署方式、运维管理、性能指标、监控告警

  - id: integration
    name: 集成对接
    description: API 接口、数据集成、第三方对接、SDK

  - id: cases
    name: 案例场景
    description: 客户案例、应用场景、成功故事、效果展示
